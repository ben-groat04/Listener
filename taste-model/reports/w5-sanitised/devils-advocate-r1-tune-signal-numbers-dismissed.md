# Devil's advocate r1 (dismissed direction), builder tune-signal-numbers

Scratch: $S/devils-advocate-r1-tune-signal-numbers-dismissed/ (code/ = my extra predictor xpredict.py + g5.py, runs/ = outputs). All my runs: harness --fast (or full for the final / null control), 2 threads. No --late / --holdout / --sealed run by me.

## 0. Bottom line
Numerically the builder's report is accurate: every number I re-ran reproduced bit-for-bit (dumps for base+OAT+stale, random joint, nested tuners identical to the builder's; null control identical). The weaknesses are in interpretation and in what is left out:
1. The report omits the harness's own pooled TUNE+LATE grade for the declared final (held-out grade removed in this copy). The report only says "does not clear 80%", true for TUNE alone.
2. Four post-hoc COMBO configs were scored on default TUNE but their default-TUNE results appear nowhere in the report. Two of them beat the "none beats default by more than +0.007" statement (+0.0111 mat0_scale+one global group; +0.0100 mat0_scale+rolling 91 d groups; lo80 -0.0000 / -0.0006) and are positive on all five alternative fold sets for cmb_mat0s_all. By the builder's own selection rule (sign consistency across fold sets) the combo dominates the declared single change.
3. The "best of 87 is inside chance best-of-N (median +0.028)" calibration pools 40 wild random configs and the stale configs with near-default ones. For the low-noise configs (own bootstrap SD < 0.004, 13 configs) chance best-of-N median is +0.0038 and the observed best (+0.0069) exceeds it (P(chance best >= observed) = 0.12). So "indistinguishable from selection among N" is overstated for the mat/partial-horizon family, which is also a monotone dose-response (mat120 +0.0004, mat30 +0.0020, mat60 +0.0043, mat60_scale +0.0069, mat0_scale +0.0062), i.e. one effect, not five independent draws.
4. "Quarter stub is real in 8 of 10 folds" is true as date arithmetic but the stub group holds 0 songs in 8 folds and 1 song in 2 folds (I counted with data.load_streams + song_table restricted to meta, as predict.py does), so the whole stub comparison tests something that is almost empty at default cutoffs. "No demonstrable effect" is then expected, not informative.
5. The effort used was 44 min of a 120 min cap; every item the report lists as "not done" costs 1-6 min per run (I ran ~25 extra models in 8 min).
6. The 80% decision rule: mat60_scale has lo80 +0.0026 (my bootstrap: +0.0026; P 0.975) vs the default on TUNE, i.e. TUNE80+ for that one config; it was set aside as a winner among 87 (see point 3), and declared mat0_scale instead although mat60_scale wins 8/10 folds (mat0_scale 5/10), but mat60_scale is negative on tune_q2 (-0.003, 80% [-0.007,-0.0002]) and flat on tune_y (+0.001).
